What this cannot prove

The limits of this report
One false accusation against an honest provider costs far more than one miss. This tool abstains when the evidence is thin rather than guessing. Please read the conclusions alongside the limits below.
  • Adjacent versions are indistinguishable. This tool resolves to tier granularity only (flagship / mid / light). Adjacent versions inside one tier — say 4.5 and 4.6 of the same line — cannot be separated without distribution baselines, so the report stops at the tier.
  • The tier call depends on sampling. Adjacent tiers can still swing on a single question. The tool abstains when the margin is narrow, which costs it some real downgrades. Use --depth forensic when the answer has to hold up.
  • Middle layers contaminate identity fingerprints. An injected system prompt and any response post-processing both change how a model expresses itself, which is why the contract layer runs first — where injection or rewriting is found, identity confidence has already been reduced accordingly.
  • Server-side weights cannot be proven. What this tool can show is whether behaviour matches expectations. It cannot show which model file the other side actually deployed.
  • Quantised builds are hard to spot. int4 and fp8 builds sit close to the original in capability, so only a probabilistic read from the tier estimate is possible — never a verdict.
  • One run describes one moment. Gradual degradation only shows up under continuous monitoring. Re-run periodically and compare against earlier reports.
  • An estimate is not an authoritative count. The metering comparison is only authoritative where the endpoint offers count_tokens. Otherwise the report uses a local estimate, and says so under "compared against".
